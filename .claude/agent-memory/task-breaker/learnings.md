## 任务粒度经验

<!-- 哪些类型的任务容易拆得太大或太小 -->

- 同文件多个功能点（如 Store 的 run_id 打标 / is_final 判定 / 压缩重构）即使都在一个大方法里，也按「写侧→读侧→新方法」的自然边界拆成独立工单，每工单 ≤10min 且可独立验证，避免把一个大方法一次改到位（难以独立验收、diff 过大）。
- 压缩算法这类「核心逻辑 + 若干兜底安全阀」的结构，拆成「核心整轮整切（K=12）」与「安全阀（硬上限/未完成轮上限/计数口径）」两个工单：核心先落地并更新既有断言，安全阀作为增量层再加测试。
- 追加实施项（如 Phase 6 A/C）若方案已在设计文档定稿，直接按「分类器/控制流」「实现/测试」自然边界拆，不必重新发现；两个实现工单若在不同文件（ModelRouter.cs vs ChatEndpoints.cs）可并行，不加 blocking edge。
- 开发者预分组「端到端最小交付切片」（matt-workflow）时，工单行头本身不再作为 ≤10min 的任务条目，而是把行内「实现要点/验收要点」checkbox 拆到 ≤10min 粒度；DAG 节点 = 工单（含测试的切片），仍与每条 blockedBy 一一对应。
- 追加「spec 外」工单（用户拍板纳入，如 agui-host T7 DevUI）时，tasks.md 需五处同步才一致：文件首「边界」段、spec 映射表下方 traceability 注（说明不在 N 条 ADDED 内，映射表不加行）、工单小节本身、文末 DAG + 文字摘要主干、边界红线与实施期确认项——且全程不触碰已勾 T1-T6 checkbox。
- 追加「测试缺陷修复」工单（如 agui-session-prod S8）时：① 不新增 spec Requirement，只在工单小节内声明它保障的是哪条既有 Requirement（含场景号）的**证据有效性**；② 只需同步 3 处（新工单小节、DAG 节点+边+主干链文字、工时汇总表含合计），§三 映射表与 §七 确认项不动；③ blockedBy 用「同改同一测试文件」的串行约束（约束 A 语境）；④ 工单内实现步骤仍按 ≤10min 拆分并配对「修复后用例通过」+「反证」两个测试项。
- 纯删除 / 瘦身型变更（chat-history-slimdown）的工单粒度：**先画「删除依赖拓扑」再切工单**——枚举「谁被谁引用 / 谁被谁的 `<see cref>` 引用 / 谁的返回类型含被删类型」，据此确定唯一可行的删除顺序；一个工单内的删除项必须是「同一依赖层」的（互相之间无删除顺序要求），跨层即拆下一工单。禁止按文件切分（三文件编译级耦合，任一中间态都编译不过）。
- 多个功能点共用一个「装配文件」时（agui-client-support 2026-09-16），DAG 的串行边**由文件重叠而非功能依赖决定**：本变更 5 项里 3 项（端点映射 / 条件 CORS / 工具 provider 实参）都要改 `src/AIShop.AguiHost/Program.cs`，即使功能上互不依赖，也必须在 DAG 里排成 T2→T4→T7 单链；反之只改各自独占文件的工单（`AguiUsernameForwarder.cs`、`Api/appsettings.json`）才是真正的并行根。拆解时先列「文件 × 工单」矩阵再定边，比按功能直觉连边更可靠。
- 向既有链路「追加一组端点」时（agui-client-support 第 6 项，2026-09-17），工单切法 = 「身份通道 → 只读端点 → 写端点（按 CRUD 分组而非按方法逐个）→ 跨面契约验证 → 收尾」：① 身份通道单列一工单（它同时被 N 个端点依赖，且是「必须传/必须校验」这类硬要求的唯一落点）；② 写端点按**语义分组**拆（「读+加购」与「改+删+清空」），把「底层仓储静默 no-op 导致 200 假成功」这类风险集中在含预检的那一组，便于配反证；③ 「跨面契约一致（逐字节）」「既有面零影响」「路由不重叠」不散落在各端点工单里，单列一个验证工单并配反证——它们断言的是**关系**而非单个端点行为。
- 全新前端 npm 工程（agui-client，2026-09-17）的工单切法 = 「地基（脚手架+测试基建）→ 数据/持久化层 → 协议层 → 各 UI 组件（互相独立的文件，可并行）→ **单页应用装配点（App.tsx）一次性收口** → 视觉核对 → 收尾验收」：① 不要按「用户可见的端到端切片」拆（每个 UI 功能单独可用需先有 App 壳，会导致 App.tsx 被 N 个工单反复改）；改为**组件先行、装配收口**——组件工单各自用 props 驱动做组件级测试（jsdom 可独立验收），装配工单只做一次（本变更 = C11，fan-in 7 条边）；② 三个共享测试助手（fetch 替身 / SSE 事件流构造 / render helper）必须在**第一个工单**建成，否则后续每个工单各写一套；③ 依赖安装一次性完成并显式禁止后续工单改 `package.json`（同文件的「装配文件」串行逻辑同样适用于 manifest）；④ design 把浏览器 E2E 列为非目标时，QA 拆成**显式人工工单**（浏览器核对 + 抓包核对）而不是硬凑自动化。

## 新增经验

- 设计文档的工时估算通常只覆盖实现，不会包含配套测试。tasks.md 需额外预算 1.5x-2x 的测试与验证时间。
- DI 相关改动（构造函数签名变更 + 注册行新增）虽然实现仅 8min，但涉及容器解析正确性和运行时行为两项独立验证，至少需要 2 个测试任务。
- 纯前端 UI 变更（HTML/CSS/JS）无法用 dotnet 单元测试覆盖，应拆分为手动浏览器验证任务，每项验证对应 spec.md 中一条具体行为。
- 改动现有行为（如压缩阈值从条数 50 改为轮次 K=12）时，既有断言测试必然被破坏——须在对应实现工单的测试配套里显式列出「更新既有断言」任务，否则实现工单无法以绿 build 收口。
- 测试工单里若包含「既有测试用例要补数据形态适配」（如 Provide 孤行 tool 用例在新配对规则下需补 run_id 或相邻 assistant-FCC），要在任务描述中点名具体用例，避免实施时漏改。
- 拆解后若开发决策拍板变更（如 schema 方案 A 幂等补列 → B 强制清库），tasks.md 须同步三处才一致：spec 映射表对应行（注明新方案 + 把「部署动作」如手动清库标为部署事项而非代码工单）、主干执行顺序/DAG（删掉受影响节点、剪掉指向边）、文件归属（受影响文件移出清单）。其余工单 ID 与 blockedBy 保持稳定，避免连锁重编号。
- tasks.md 有写权限门禁（仅 task-breaker 可写，implementer 被 check_openspec_gate.py 拦截，但对 **Edit** 不成立——2026-09-16 T1 实证 implementer 用 Edit 勾选未被拦截）→ Step 4 完成后可由 implementer 自行勾选，失败时转 @task-breaker 回灌；勾选依据 = handoffs/ 下对应 handoff 文件存在 + git log 有对应 commit。Step 5 评审发现的清理项（如 unused using CS8019）追加为独立 T-FIX-N 工单（blockedBy: 无、DAG 加独立节点、单独 commit），保持与已实施工单解耦。
- 追加实施项若超出 spec.md 范围（如 Phase 6 A/C），tasks.md 需显式标注「不在 spec 16 条内」并在 spec 映射表外维护 traceability（引用设计文档 §3），避免 implementer 误以为漏了 spec 映射行；方案 B 存档不实施要写进边界说明，防止被误拆。
- 高风险外部依赖（外部 NuGet 包可用性 / 原生二进制 / 框架组件兼容性）变更：拆一个「基础设施 POC 验证」工单作 DAG 根（无依赖最先执行），把 design 风险表里标「高」的项列成显式验证任务，并写明失败处置（回设计调整/降级方案）；后续实现与集成工单显式 blockedBy 该 POC 工单，避免把外部风险带进主链路到很晚才暴露。
- 一个实现类内部若包含「核心逻辑 + 若干兜底/增量机制」且分属不同文件（如 RagIndexer 的 Rebuild/EnsureIndexed 与 Upsert/Remove/HostedService），按「核心构建 → 增量/兜底」自然边界拆两个串行工单，每工单 ≤60min 可独立验收；同 class 的两接口方法（如 RagSearchService 的 SearchProducts/SearchKnowledge）不跨工单拆分，保持类完整性。
- preview/预发布包（如 AG-UI Hosting 1.20.0-preview）API 拆解时：涉及装配/挂载的工单把「API 面以本地镜像源码为准」写进实现要点，测试工单给「尽力而为 + 降级预案」双轨（如请求级离线驱动不可行则降级为路由冒烟 + 纯函数单测，行为移交 E2E 人工验收），避免拆解承诺超过可验证范围。
- preview API 拆解前先读本地镜像源码实证关键契约（agui-host T7 案例）：`MapAGUIServer` keyed 重载签名、DevUI `/v1/entities` 实体发现机制（keyed AIAgent 枚举）、`MapDevUI` 的 auth/loopback 结构、CPM 实际锁定版本（发起方转述版本号可能错，如 Hosting.OpenAI 实为 alpha 非 preview）——用源码把「不确定 API」转为「确定事实」再落 checkbox，显著降低实施期反复。
- 「多个追加工单同改同一装配文件」且各自 blockedBy 相同基线（agui-host T12-T14 案例）：即使每个工单技术上只依赖基线 T11，只要它们触碰同一装配面（AGUIShoppingAgent.cs / Program.cs / AguiServiceCollectionExtensions.cs），就应把 DAG 定为强制串行（T11→T12→T13→T14），并在 DAG 文字摘要里写明「同文件改动勿并行」的约束与串行理由；避免实施期同文件并发改造成 rebase/合并噪音。
- 追加装配类工单若涉及「框架内建 hook 不明显」的能力，先读镜像源码找注册/装配挂点再落 checkbox（agui-host T12/T13/T14 案例）：T12 会话持久化挂点 = `MapAGUIServer` 的 `GetKeyedService<AgentSessionStore>(agent.Name)`（未注册 Noop = ephemeral），T14 工具上限挂点 = MAF 默认中间件注入的 MEAI `FunctionInvokingChatClient.MaximumIterations`（ChatClientAgentOptions 无该旋钮），T13 记忆挂点 = `AIContextProviders`（同 CompactionProvider 并列）+ `AddMemoryService` 参数化——把「哪一层改哪个选项/注册哪个服务」写清，实施者按图索骥，少走弯路。
- 拆「老能力参数化 + 新宿主挂载」双段工单（agui-host T13 案例）：老代码改动（AddMemoryService 加可选 databasePath，仿 T2 AddRagService 参数化）+ 老记忆测试护航 是独立可验收段，新宿主装配（独立库 + MemoryContextProvider 挂载 + 写入时机）是另一段；并把老代码改动显式标注为「第二个动老代码处」（T2 之后），在 spec 映射表下方注明，避免与「T2 是唯一动老代码处」的既有表述冲突。
- 「把既有真实模型人工 E2E 固化为可进 CI 的 mock-LLM 集成回归」类纯测试工单（agui-host T16 案例）拆解要点：① mock 只替换**模型 seam**（C5 `IModelChatClientFactory` stub），工具/EF/RAG 全走真实——断言链是「真实 AG-UI wire → 真实工具执行 → DB 副作用」，这正是验收自动化的核心价值；② 用「输入是否已含目标工具 `FunctionResultContent`」做 mock 分阶段决策（先 FCC 后最终文本），覆盖 FICC 工具迭代（`GetResponseAsync`）与 SSE 出口（streaming）双入口；③ 落库断言要能把业务库指到隔离临时文件 → 需 1 处 Program 装配 seam（连接串可选读、缺省常量回退、无键零行为变化），靠既有 WAF 测试缺省回归证明；④ 涉及真实语义检索命中的断言要识别「外部前置」（bge 模型文件是否在测试输出）并给降级预案，避免拆出不可能在 CI 绿的承诺；⑤ 与既有「纯文本 mock」区分开——现有 `CreateMockChatClient` 不产出 FCC，E2E 必须新写脚本化工具 mock helper。
- 压缩/裁剪类变更的「触发条件测试口径」（agui-session-prod 案例）：当框架策略的触发阈值由 token 规模决定（官方 `ContextWindowCompactionStrategy` 截断阈 ~89292 token），不要据此拆「构造 token 级长历史」的昂贵测试；改用**同变更新增的确定性硬上限**（如 `Agui:SessionMaxRounds`）作触发，token 阈值路径交给「阈值常量断言」覆盖，并把「是否补 token 级跨阈值 e2e」显式列为实施期裁决项。
- 「异常不阻断/不退出」类容错的**可测性设计**（agui-session-prod 案例）：① 「压缩失败不阻断落库」的测法 = 在依赖注入点传入一个 `CompactCoreAsync` 抛异常的测试用 `CompactionStrategy` 子类（`trigger` 用 `CompactionsTriggers.Always`），而非人为构造畸形输入去碰运气；② 「后台服务单次异常不退出」的测法 = 让依赖指向不可写路径（不存在的目录）使其必然抛异常，断言后台 `Task` 延时后仍未完成（存活）再 `StopAsync`；③ 后台服务「周期」以小时计时不必为测试改成亚小时——只要服务**启动即先清一次**，测试即可在不引入短周期配置的前提下验收。
- 工作区含发起方「开发者自己的未提交改动」时（agui-session-prod 案例）：tasks.md 必须在**文件首**单列「全局装配约束」三条——① 同文件改动串行（用 blockedBy 串成链，禁并行）；② 提交一律 `git add <pathspec 精确文件>`、**禁 `git add -A`/`git add .`**，且不得覆盖/回退既有 dev 改动；③ 红线目录清单（只允许改哪两个目录）。并把 pathspec 要求在**每个工单的 commit checkbox 里重复**（不只在文件首写一次），避免实施者按习惯批量 add。
- 识别并修复「断言空转 / 虚假保证」（false assurance）类测试缺陷（agui-session-prod S8 案例）：① 征兆 = 测试用**相对路径 / 进程 CWD** 定位被测资源（`Path.GetFullPath("aishop.db")` 在 xUnit 下解析到 `bin/Debug/net10.0/`，真实资源在仓库别处）→ 前后快照两端同为 `MISSING` → `Assert.Equal(before, after)` 恒真；② 修复 = 用 `AppContext.BaseDirectory` 上溯找含 `AIShop.sln` 的仓库根定位资源，且**期望资源缺失即显式失败**（不可静默处理 missing）；③ 判定修复是否真有断言力的标准 = **反证**——把某资源路径改成不存在后该用例**必须失败**（若仍通过则修复无效：这正是「只对『三者全缺』才失败」的弱版失败原因）；④ 此类修复工单归为缺陷修复、不新增 spec Requirement，只在工单小节标注它保障哪条 Requirement 的证据有效性；⑤ 同一手法可用于「代码库静态无残留」类断言（读源码前先定位仓库根）。
- 「纯删除 / 瘦身型」变更的拆解流程（chat-history-slimdown 案例）：① 先枚举**编译级耦合边**（属性删除 → 测试引用失效；类型删除 → 返回类型失效；成员删除 → `<see cref>` 触发 CS1574 在 `TreatWarningsAsErrors` 下失败），据此把工单排成**删除依赖拓扑上的单链**，并在 tasks.md 的 DAG 摘要里显式写「本变更无并行分支」及其编译级理由；② 删除顺序 = 依赖方先删（注释掉的死实现 → 只被它调用的方法 → 依赖被删类型的成员/返回类型 → 配置属性 + **必须在同一工单**适配其测试引用）；③ 注释重写不要集中成一个工单——归属跟着「哪次删除破坏它的 cref / 语义」走，否则中间态要么编译失败、要么留下「注释说 A、代码做 B」（Provide remarks 随 T1、Store/State remarks 随 T3、类 remarks 随 T5）；④ 纯删除工单的配对测试用**既有用例回归**（证明未误删活代码），真正新增的断言只覆盖「行为真变了」的点（本次仅 3 类：不查库、配置面、静态无残留）；⑤ 保留行为一律写「既有用例仍绿 + 对应 spec 场景号」，**不为保留行为硬造重复用例**（发起方会明确禁止）。
- 「不查库 / 不访问某资源」这类**否定性行为**的可测性写法（chat-history-slimdown 案例）：断言「未发生访问」要靠**把访问路径变成必然失败**（连接串指向不存在目录 → 若真访问必抛异常），再断言「调用正常返回 空/成功」；只断「返回空」的用例是恒真空转（发起方明确禁止，design 也写明）。同理，否定性「成员不存在」断言用**反射 GetProperty == null**，而非「找不到就跳过」。
- 收尾回灌时若**计划本身已被推翻**（chat-history-slimdown 案例，2026-09-15）：勾选不是机械动作，须逐条核对「该 checkbox 描述的事是否真的发生过」——本次 T5 第 4 项写「三红线文件均未提交」，但收尾 commit 里 `SqliteAgentSessionStore.cs` **确实**因新增兜底被改，前提失效 → 处理方式不是勾 [x] 了事，而是**在同行末尾追加 `→ 更正（日期）：…`** 就地留痕，说明哪条前提失效、哪些仍成立。同时追加「收尾记录」章节如实登记三类偏差：① 计划条目未执行（T3/T4）；② 计划新增的产物已删除（两个测试文件）；③ 核验前提失效。教训：**tasks.md 不会随代码演进而自动失效**，收尾必须显式记录「哪些条目已不反映实际」，且偏差只写事实、不辩解不美化。
